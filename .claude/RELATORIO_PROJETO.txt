1. VISÃO GERAL DA ARQUITETURA
================================================================================

O QUE É
  Um poker Texas Hold'em online multiplayer em tempo real, com uma moeda
  interna (₿C — Bitchager) que pode ser comprada com dinheiro real (PIX via
  Mercado Pago) e sacada de volta pra PIX (hoje de forma manual/assistida).

PEÇAS DO QUEBRA-CABEÇA (onde cada coisa mora)

  FRONTEND
    - React 19 + Vite, hospedado no Vercel
    - URL: https://poker-game-tawny-rho.vercel.app
    - Fala com o backend via Socket.io (tempo real) + algumas rotas REST
      (GET /mesas, GET /ranking, GET /jogador/:uid)

  BACKEND
    - Node.js + Express + Socket.io, hospedado na Hostinger (hospedagem
      compartilhada, "Implante web app" — puxa direto do GitHub)
    - URL: https://brown-wolverine-631802.hostingersite.com
    - IMPORTANTE: todo estado de jogo (mesas, torneios) fica só em MEMÓRIA
      (um Map do JavaScript). Não está salvo em nenhum banco de dados.
      >>> Isso significa que TODA VEZ que o backend reinicia (o que
      >>> acontece a cada deploy novo), TODAS as mesas e torneios em
      >>> andamento são perdidos. Ver seção 4 (pendências) pra mais detalhes.

  BANCO DE DADOS / LOGIN
    - Firebase Auth (login por Google ou email/senha)
    - Firestore (banco de dados): perfil do jogador, saldo, transações,
      blockchain interna, depósitos/saques pendentes
    - Projeto Firebase: poker-texas-hold-1ec8d

  PAGAMENTOS
    - Mercado Pago, credenciais de PRODUÇÃO (não é mais teste)
    - Depósito: automático, via PIX, com webhook de confirmação
    - Saque: manual — fica pendente até o admin (você) confirmar que pagou
      o PIX pelo app do banco (a API do Mercado Pago não oferece, hoje,
      um jeito de mandar PIX pra uma chave qualquer automaticamente)

  REPOSITÓRIO
    - GitHub: github.com/walterlandev/poker-game (era wassites, a conta
      mudou de nome/dono em algum momento)
    - git push na branch main = deploy automático nos dois lados
      (Vercel pro frontend, Hostinger pro backend)

2. COMO CADA PARTE DEVERIA FUNCIONAR
================================================================================

--------------------------------------------------------------------------
2.1 CADASTRO E LOGIN
--------------------------------------------------------------------------
  - Duas formas de entrar: "Continuar com Google" ou email/senha
  - Cadastro novo: cria o perfil no Firestore com saldo ZERO (saldo real e
    bônus) — o bônus de boas-vindas só é creditado depois, quando o
    jogador resgata ele manualmente na Carteira (não é automático)
  - Depois do cadastro, é OBRIGATÓRIO criar um PIN de segurança (4+
    dígitos) antes de poder jogar — sem PIN, não dá pra depositar, sacar,
    comprar na loja nem enviar ₿C pra outro jogador
  - Jogadores que já tinham conta de antes de o PIN existir também são
    obrigados a criar o PIN na primeira vez que tentam usar a carteira

--------------------------------------------------------------------------
2.2 LOBBY (tela principal, depois de logar)
--------------------------------------------------------------------------
  Abas: Carteira | Mesas | Torneio | Ranking | Loja | Admin (só se for admin)

  - CARTEIRA: saldo (real + bônus), depositar, sacar, enviar ₿C, extrato
  - MESAS: lista de mesas públicas e privadas com vaga (< 9 jogadores) —
    inclusive mesas já em andamento, mostradas com o selo "Em jogo" e
    botão "Observar / Entrar" (quem entra senta e é servido a partir da
    próxima mão; não existe modo espectador-só-observando de verdade,
    "Observar" aqui é só o texto do botão). Só some da lista quando fica
    CHEIA (9 jogadores). Atualiza sozinho em tempo real quando uma mesa é
    criada, muda de fase, enche ou é fechada (não precisa recarregar).
    (Mudou em 24/07/2026 — antes sumia da lista assim que o jogo
    começava; um jogador com 2 contas testando notou que a própria mesa
    "sumia" pra ele mesmo e pediu pra mudar esse comportamento.)
  - TORNEIO: torneios abertos, criar torneio, entrar via convite
  - RANKING: top jogadores por pontuação
  - LOJA: comprar ₿C com dinheiro real, comprar temas/baralhos diferentes
  - ADMIN: só visível/funcional pra quem tem isAdmin=true no Firestore
    (checado no SERVIDOR, nunca só escondido na tela)

--------------------------------------------------------------------------
2.3 CRIAR / ENTRAR EM MESA
--------------------------------------------------------------------------
  - Criar mesa: escolhe nome, valor de entrada (buy-in), blinds, quantos
    bots, se é privada (com senha) ou não
  - Buy-in é debitado do saldo real do jogador (saldo + bônus) na hora
    de criar ou entrar na mesa
  - Mesa PRIVADA exige a senha certa pra qualquer um que ainda não esteja
    sentado — sem a senha certa, não entra
  - Mesa aparece na lista pública (aba Mesas) até ela ficar CHEIA (9
    jogadores) — continua na lista mesmo depois do jogo começar (ver
    2.2 acima)
  - Convite por link: dentro da mesa (enquanto ainda está "Aguardando"),
    tem um botão "Convidar amigos pra mesa" que copia um link
    (?mesa=CÓDIGO) — quem abre esse link entra direto na mesa
    automaticamente (mesmo esquema já existia pra torneio)

--------------------------------------------------------------------------
2.4 O JOGO EM SI (motor de poker)
--------------------------------------------------------------------------
  - Texas Hold'em padrão: 2 cartas na mão, 5 cartas comunitárias
    (Flop 3 + Turn 1 + River 1), rodadas de aposta em cada fase
  - Dealer (botão) roda a cada mão. Heads-up (só 2 jogadores): dealer é
    o Small Blind e age primeiro no pré-flop, mas por último nas fases
    seguintes — regra padrão de poker
  - Fold / Check / Call / Raise / All-in — cada botão só deveria estar
    disponível/clicável quando a ação é realmente possível (ex: não dá
    pra fazer Check se tem aposta na mesa; não dá pra fazer Raise se o
    saldo não cobre nem o aumento mínimo)
  - All-in incompleto: se o jogador não tem saldo pra igualar a aposta,
    ele entra "all-in" só com o que tem, e isso NÃO reabre a rodada de
    apostas pros outros (regra padrão)
  - Side pots (potes divididos): quando alguém vai all-in com menos saldo
    que os outros, o pote se divide em "pote principal" (todo mundo
    disputa) e "pote lateral" (só quem apostou mais disputa). O dinheiro
    de quem DESISTIU (fold) no meio do caminho continua contando pro
    valor do pote — só a ELEGIBILIDADE de ganhar é restrita a quem não
    desistiu.
  - Showdown: mostra as cartas de quem chegou até o fim, calcula a mão
    mais forte, distribui o(s) pote(s), mostra o resultado na tela por
    alguns segundos antes de começar a próxima mão
  - Sair da mesa no meio de uma mão em andamento: conta como desistência
    (fold) automática — se só sobrar 1 jogador ativo, ele ganha na hora
  - Fichas que sobraram na mesa voltam pro saldo real do jogador quando
    ele sai da mesa
  - Recompra (rebuy): se o jogador zerar as fichas NA MESA (mas ainda tem
    saldo real ou bônus fora da mesa), aparece um botão pra comprar mais
    fichas (mesmo valor do buy-in original) e continuar jogando — ou um
    botão pra simplesmente sair da mesa, se não quiser/não puder recompor
  - Jogador sem fichas fica sentado observando (não participa da mão)
    até recomprar ou sair — nunca é dado como perdedor forçado
  - Timeout: 45s pra jogador humano agir, 10s pra bot. Depois de 3 faltas
    seguidas, o jogador é removido automaticamente da mesa (e o que
    sobrou de fichas dele volta pro saldo real)

--------------------------------------------------------------------------
2.5 BOTS
--------------------------------------------------------------------------
  - Preenchem vagas na mesa quando o host escolhe adicionar bots
  - Têm uma IA baseada na força da mão + agressividade aleatória por bot
  - Fazem rebuy automático quando zeram (não ficam presos esperando)

--------------------------------------------------------------------------
2.6 TORNEIOS
--------------------------------------------------------------------------
  - Buy-in fixo, fichas iniciais fixas, várias mesas em paralelo que vão
    se fundindo conforme jogadores são eliminados
  - Rebuy period configurável no início do torneio
  - Campeão leva o prêmio total acumulado (buy-ins de todos + rebuys) —
    creditado automaticamente no saldo real dele quando o torneio acaba
  - Convite por link (?torneio=CÓDIGO), igual mesa comum

--------------------------------------------------------------------------
2.7 CARTEIRA (saldo real x bônus)
--------------------------------------------------------------------------
  REGRA DE OURO: saldo REAL pode ser sacado; saldo BÔNUS não pode nunca
  ser sacado (só jogado). Os dois juntos contam pra entrar em mesa/torneio.

  - DEPOSITAR: escolhe valor em R$, gera um PIX real (QR Code + copia e
    cola) via Mercado Pago, fica PENDENTE até o Mercado Pago confirmar o
    pagamento (webhook automático credita o ₿C na hora que confirma)
  - SACAR: exige ter PIN configurado, chave PIX de destino, valor mínimo
    de ₿C 5.000, taxa de 3%, limite diário. Fica PENDENTE até o ADMIN
    confirmar manualmente que pagou o PIX pelo próprio banco (ver seção
    4 — a API do Mercado Pago não manda PIX pra qualquer chave sozinha)
  - ENVIAR ₿C: manda saldo pra outro jogador (busca por nome/ID), com
    taxa. Servidor sempre recalcula a taxa e o total — nunca confia no
    que o cliente manda
  - BÔNUS DE BOAS-VINDAS: resgatado manualmente uma vez só, vira saldo
    BÔNUS (não saldo real)
  - EXTRATO: histórico de tudo (depósito, saque, envio, recebido, prêmio,
    compra, bônus), com filtro por tipo e período, mostra o status de
    cada transação (pendente/confirmada)

--------------------------------------------------------------------------
2.8 BLOCKCHAIN INTERNA (ledger auditável)
--------------------------------------------------------------------------
  - NÃO é uma criptomoeda de verdade nem negociável fora do jogo — é um
    livro-razão interno, tipo blockchain de verdade (blocos encadeados,
    prova de trabalho, hash), só pra ter um registro auditável e à prova
    de adulteração de todas as movimentações de ₿C
  - Toda transação de saldo real (depósito, saque, envio) entra nesse
    ledger também, em paralelo ao Firestore (que é a fonte real do saldo)
  - Minerado automaticamente a cada 20s se tiver transação pendente
  - Persistido no Firestore — sobrevive a reinícios do servidor
  - Jogador pode conferir o próprio histórico e validar a integridade da
    cadeia pela tela da Carteira

--------------------------------------------------------------------------
2.9 LOJA (temas/baralhos)
--------------------------------------------------------------------------
  - Compra temas de carta diferentes com ₿C (visual: cores, baralho
    "premium" com bordas/detalhes especiais)
  - O tema ativo do jogador aparece PRA TODO MUNDO na mesa (não só pra
    ele) — cada jogador vê o baralho de cada adversário com o tema que
    ELE escolheu, não o seu próprio

--------------------------------------------------------------------------
2.10 PERFIL (foto e dados)
--------------------------------------------------------------------------
  - Foto de perfil: escolhe entre avatares prontos OU sobe uma foto do
    celular/computador — a foto enviada fica visível pros outros
    jogadores na mesa (sobe pro próprio servidor, não pro Firebase
    Storage, que exigiria plano pago)
  - Nome, telefone, email editáveis

--------------------------------------------------------------------------
2.11 PAINEL ADMIN
--------------------------------------------------------------------------
  - Só acessível por quem tem isAdmin=true no Firestore (checado sempre
    no servidor)
  - Usuários: lista todo mundo, saldo real/bônus, se tem PIN, data de
    criação da conta
  - Depósitos pendentes: mostra os que ainda não foram confirmados
  - Saques pendentes: mostra valor, chave PIX, NOME do titular da conta
    (pra conferir se bate com quem é dono da chave PIX antes de mandar o
    dinheiro), botão de copiar a chave, botão "já paguei — confirmar"

3.1 SESSÃO 24/07/2026 — AUDITORIA GERAL + CORREÇÕES
================================================================================
  Pedido do usuário: analisar o relatório e o jogo inteiro, achar o que

  FINANCEIRO / SEGURANÇA (crítico)
  [x] Buy-in negativo/inválido permitia creditar ₿C em vez de debitar
      (criar_mesa, entrar_mesa, criar_torneio, entrar_torneio, rebuy) —
      debitarEntradaMesa agora valida e normaliza o valor
  [x] CRÍTICO: bônus (não sacável) virava saldo real sacável ao sentar
      numa mesa e sair de novo, e também ao enviar ₿C pra outra conta —
      agora rastreamos "origemBonus" por jogador na mesa e
      creditarSaidaMesa/wallet:enviar nunca devolvem mais bônus do que
      realmente entrou como bônus
  [x] Taxa de depósito vinha do cliente e nunca era recalculada no
      servidor (TAXA_DEPOSITO existia mas não era usada) — corrigido
  [x] Faltava checagem de PIN na compra de tema na Loja — corrigido
      (mesmo padrão de PinConfirm já usado em depósito/saque/envio)
  [x] Corrida no crédito de depósito via webhook (reenvio do Mercado
      Pago podia duplicar o crédito) — idempotência + crédito agora
      atômicos na mesma transação Firestore
  [x] Webhook do Mercado Pago aceitava requisição sem checar assinatura
      se MP_WEBHOOK_SECRET estivesse vazio — agora rejeita em produção
      nesse caso (só não bloqueia em modo dev, sem token real)

  TORNEIO (crítico)
  [x] CRÍTICO: mesa de torneio encerrava a rodada inteira na primeira
      mão em que todos exceto um desistissem (W.O.), mesmo com todo
      mundo ainda de fichas cheias — na prática isso quebrava qualquer
      torneio, já que a maioria das mãos termina por fold, não showdown
  [x] CRÍTICO: sair/desconectar de mesa de torneio creditava o stack
      da mesa como saldo real na hora — furava o winner-take-all. Agora
      é tratado como forfeit (fichas de torneio não são dinheiro fora
      dele) e o jogador é marcado eliminado no bracket
  [x] Rebuy podia ser cobrado com o torneio já finalizado (cliente
      desatualizado) — checarRebuy agora exige torneio 'em_andamento'

  MOTOR DO JOGO (regras do poker)
  [x] CRÍTICO: ordem de turno quebrava quando um jogador saía da mesa
      (ou era removido por inatividade) no meio de uma mão com 3+
      jogadores — podia pular quem ainda precisava agir. Descoberto e
      confirmado com um script Node (socket.io-client) simulando a
      partida real
  [x] CRÍTICO: consequência do bug acima — se quem saísse fosse
      justamente a referência de "volta completa" da rodada de apostas,
      a mão travava num loop infinito de check, nunca fechava a rodada
  [x] Botão do dealer "resetava" pro início da lista de jogadores
      quando o dealer anterior zerava fichas ou saía da mesa, em vez de
      passar pro próximo jogador realmente ativo (afeta justiça do
      rodízio de blinds)
  [x] Fichas de quem saía da mesa no meio de uma mão com side pot em
      aberto podiam ser somadas ao pote errado (a fração paga por ele
      antes de sair precisa entrar na faixa certa de side pot)
  [x] Rebuy automático de bot rodava tarde demais — bot recompunha o
      saldo mas ficava de fora justo da mão em que devia voltar
  [x] Rebuy não validava que o valor era exatamente o buy-in da mesa
  [x] GET /mesas não filtrava mesas já cheias (9/9) — apareciam no lobby
      mesmo sem vaga
  [x] adicionarBot não avisava o lobby em tempo real (mesas_atualizadas)

  FRONTEND
  [x] <style> solto dentro de ActionBar.jsx e HandStrength.jsx — as
      duas telas mais visitadas do jogo (montam/desmontam a cada
      fold/all-in/mão nova) — regressão exata do padrão que já causou
      o bug de tela preta. Movido pro CSS global em main.jsx
  [x] Timer de ação (Temporizador.jsx) contava localmente a partir do
      momento em que o componente montava, dessincronizado do timeout
      real do servidor (refresh de página no meio do turno bugava a
      contagem) — servidor agora manda um prazo absoluto
      (mesa.turnoExpiraEm) e o frontend conta a partir dele
  [x] Vazamento de listener de socket em ModalCriarMesa.jsx (sem
      cleanup no timeout) — risco de criar mesa em duplicidade com
      duplo débito de buy-in
  [x] Botão Call mostrava o custo cheio mesmo quando o saldo não
      cobria (deveria mostrar "All-in ₿C X", já que é isso que o
      servidor realmente processa)

  COMO FOI TESTADO

      (sentar a vítima numa mesa junto com uma segunda conta própria e
      sacar o saldo real dela via sair_mesa, sem PIN/taxa/limite).
      Corrigido: frontend agora manda idToken real do Firebase
      (auth.currentUser.getIdToken()) junto no 'autenticar'; backend
      verifica com admin.auth().verifyIdToken() (nova função
      verificarIdToken em firebase-admin.js) e usa SEMPRE o uid do
      token verificado, ignorando o uid que o cliente alegou. Em modo
      offline (sem Firebase, testes locais) continua confiando no uid
      puro, já que não tem como verificar token sem o Admin SDK ativo.
  [x] CRÍTICO: criar_mesa repassava config.smallBlind quase direto do
      cliente pro game-manager (só `|| 10`, que não bloqueia negativo).

      sido aplicado ao smallBlind. Corrigido em game-manager.js

      criarMesaTorneio não precisou de correção — o valor já vem
      calculado no servidor pelo tournament-manager.js, nunca do
      cliente.

RISCO ALTO — Estado do jogo só em memória
  Mesas e torneios ativos vivem só na memória do processo Node. Toda vez
  que o backend é reiniciado (todo deploy novo faz isso), esse estado é
  perdido — jogos em andamento simplesmente desaparecem, mesmo que os
  jogadores continuem "vendo" a tela antiga até recarregar.
  → Solução de verdade: persistir mesas ativas em algum lugar durável
    (Firestore ou Redis). Isso é um trabalho de verdade, não um ajuste
    rápido — envolve reestruturar bastante o game-manager.js.
  → Enquanto isso: evitar reiniciar o servidor durante partidas reais,
    ou avisar os jogadores antes de um deploy.

CORRIDA NO CADASTRO PODE PULAR A CRIAÇÃO DO PIN
  Descoberto em 24/07/2026 testando o cadastro ponta-a-ponta (ver seção
  3.2). CriarPin.jsx depende do socket já estar conectado pra salvar o
  PIN (emite 'wallet:criar_pin' e espera 'wallet:pin_criado'), mas quem
  conecta o socket de fato só roda depois que o wizard de cadastro
  termina — a única forma de já estar conectado nesse meio-tempo é o
  onAuthStateChanged (App.jsx) ganhar a corrida contra a escrita do
  Firestore feita por criarPerfil(). Se perder essa corrida, a etapa
  "Criar PIN" trava pra sempre em "Salvando...", sem nenhum erro visível.
  Reproduzido de forma consistente localmente. Não corrigido ainda —
  fora do escopo da sessão em que foi achado.
  → Possível correção: CriarPin.jsx conectar o socket ele mesmo (ou
    App.jsx conectar assim que o Firebase autentica, sem depender do
    getDoc do Firestore terminar primeiro).

FOTO DE PERFIL: NÃO SABEMOS SE SOBREVIVE A UM DEPLOY
  O usuário perguntou (24/07/2026) se guardar a foto de perfil no
  próprio disco da Hostinger (backend/public/avatares/, servido em
  /avatares — é o que já está implementado, ver seção 2.10) é uma
  solução válida pra foto aparecer pros adversários. Testado ao vivo
  contra produção: upload funciona, a URL retornada já é absoluta
  (usa SERVER_URL), então QUALQUER jogador vê a foto normalmente hoje
  — isso não é o problema.
  O que ficou em aberto: essa pasta não é rastreada pelo git (não tem
  nem entrada no .gitignore, simplesmente nunca foi commitada) e o

  deploy, os arquivos enviados sobrevivem tranquilamente (git pull não
  mexe em arquivo não rastreado). Se ela faz um clone limpo / apaga a
  pasta do app inteira a cada deploy, todo avatar enviado por usuário
  é perdido a cada push — e o campo `avatar` no Firestore ficaria
  apontando pra uma URL 404.

  (conta de teste já apagada do Firebase, mas o arquivo em si não pode
  ser removido sem acesso ao filesystem da Hostinger). Da PRÓXIMA vez

TORNEIO NÃO TEM MERGE DE MESAS DE VERDADE
  Descoberto na auditoria de 24/07/2026: cada rodada do torneio cria
  mesas novas (uma por grupo de jogadores) que jogam até sobrar 1
  vencedor CADA UMA, e só então a próxima rodada é montada com os
  sobreviventes — resetando o stack de todos pro valor inicial de novo.
  Não existe "fundir mesas conforme jogadores vão sendo eliminados"
  como o documento da seção 2.6 descreve — é mais parecido com um
  formato de bracket (Sit & Go em série) do que um MTT clássico com
  merge dinâmico. Funciona e é justo, só não é literalmente o que está
  descrito. Construir merge de mesas de verdade é trabalho arquitetural
  grande (mexer a fundo no game-manager.js e tournament-manager.js),
  não um ajuste rápido — fica pra quando for priorizado.

BACKEND/NODE_MODULES É RASTREADO PELO GIT (achado em 04/08/2026)
  Descoberto ao investigar por que um `npm audit fix` no backend
  aparecia como milhares de arquivos alterados no `git status`:
  `backend/node_modules/` está COMMITADO no repositório (6181+
  arquivos rastreados), apesar do `.gitignore` da raiz listar
  `node_modules`. Isso só é possível porque foi commitado antes dessa
  entrada existir (ou direto, ignorando o .gitignore) — o .gitignore
  não afeta arquivos já rastreados. `frontend/node_modules/` NÃO é
  rastreado (só o backend). Bate com a suspeita de que a Hostinger
  provavelmente só faz `git pull` + restart (sem rodar `npm install`
  no servidor) — por isso o node_modules precisa vir pronto no commit.
  → Implicação prática: qualquer atualização de dependência do backend
    (ex: `npm audit fix`, `npm update`) só faz efeito em produção se o
    `node_modules` atualizado for commitado E pushado junto — só mudar
    package.json/package-lock.json não basta como bastaria num projeto
    normal.

RELATÓRIO DE VULNERABILIDADES NPM (04/08/2026) — CORRIGIDO
  Usuário trouxe um relatório (provavelmente GitHub Dependabot, dado
